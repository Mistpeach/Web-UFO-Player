# 远程中继服务器 · 实现原理

> 这份文档解释**为什么这样设计**。部署操作看 `deploy/部署教程-小白向.md`，协议字段看 `PROTOCOL.md`。

---

## 1. 它解决的是什么问题

浏览器的 Web Bluetooth（`navigator.bluetooth`）**只能操作本机的蓝牙**。这是浏览器安全模型决定的，
没有任何办法让另一台设备通过网页去操作用户本机浏览器的蓝牙连接。

所以"远程控制"唯一可行的形态是：

```
[玩具 UFO-TW] ◄──BLE──► [被控方浏览器]  ◄──wss──►  【服务器】  ◄──wss──►  [主控方浏览器]
                         · 唯一持有蓝牙               只转发                · 发指令、看状态
                         · 本地 20Hz 发包
```

**由此推出两条硬约束：**

1. **被控方页面必须一直开着** —— 它是蓝牙的唯一持有者
2. **服务器只是个"会转发的房间"** —— 它不碰蓝牙，也不理解业务

## 2. 数据流

```
主控方改了强度
    │
    ├─ 主控端 session.setState() → rev+1，标记 dirty
    │
    ├─ 下一个 tick（50ms 粒度）→ 构造 STATE 消息
    │    · 只带"对端还没确认拥有"的波形（通常 0 个）
    │    · payload 里含 rev / running / beatKey / 两通道参数
    │
    ▼
服务器收到 {t:'relay', payload}
    ├─ 不解析 payload
    ├─ 补一个 s（自己的时间戳）
    └─ 转发给房间内其他成员
    │
    ▼
被控方收到 STATE
    ├─ protocol.validate() 校验字段类型与范围（畸形直接丢）
    ├─ 波形指纹校验（防止内容被篡改但指纹没变）
    ├─ 引用的波形必须都在缓存里，否则不应用
    ├─ 应用到本地引擎（setWave / setIntensity / setPhase / setEnabled）
    └─ 回 ACK（捎带：被控蓝牙状态 + 实际输出 + 时钟读数 + 被控↔服务器延迟）
    │
    ▼
主控方收到 ACK
    ├─ 比对 digest：一致 → 停止重传（confirmed）
    │              不一致 → 退避重传（resending）
    └─ 更新界面：被控蓝牙状态、被控实际输出、端到端延迟
```

**关键点：网络上跑的是"期望状态"，不是逐帧指令。**
被控方按期望状态**自己在本地以 20Hz 生成实际指令**发给玩具。
所以网络延迟只影响"参数生效那一刻"的体感，**完全不影响波形本身的质量**。

## 3. 房间生命周期

```
① 被控方连上蓝牙 → 连服务器 → 发 create
   服务器：生成 8 位数字房间号（查重）→ 回 created(role:slave)
   房间进入 idle 计时

② 主控方发 join(<房间号>)
   服务器：校验存在 + 人数未满 → 回 joined(role:master)
        → 向房间内其他人推 peer(event:'joined')
   房间人数 = 2

③ 双方开始通过 relay 互发业务消息
   每次收到 relay 都刷新该房间的 idle 计时

④ 任一方离开（主动 leave 或连接断开）
   服务器：把它从 members[] 移除
        → 向剩下的人推 peer(event:'left')
        → 被控方收到后立即安全停机

⑤ 房间空闲超过 room.idleMs（默认 10 分钟）
   服务器：回收房间（从 rooms 里删掉），房间号可被再次使用
```

**为什么房间号是服务器生成的**：避免两个房间撞号；也让房间号与任何设备信息无关，不可反推。

## 4. 为什么服务器不解码 payload

这是刻意的设计决定，带来三个好处：

| 好处 | 说明 |
|---|---|
| **协议升级不用动服务器** | 客户端业务协议怎么改都行，服务器只当它是"一个对象" |
| **可审计** | 自建者一眼就能看出服务器没做任何"聪明事"，只转发 |
| **省 CPU 与流量** | 不做解析、不做重组、不做校验 —— 只是把字符串搬过去 |

代价是：服务器**不能**做业务级校验（比如"这个强度值合不合法"）。
所以**业务校验必须由客户端自己做**——客户端收到任何消息都先过 `protocol.validate()`，
字段类型不对、数值越界、波形指纹不匹配，一律丢弃。这是安全责任划分的结果，不是漏洞。

## 5. 为什么"失联停机"必须由客户端执行

这一点非常重要，值得单独讲清楚。

**设想：如果让服务器来负责停机会怎样？**

- 服务器要理解业务 → 违反了第 4 节的设计
- 服务器要知道"被控方现在开着输出" → 要维护业务状态
- **服务器自己挂了怎么办？** 它都挂了，谁来发停机指令？→ 设备可能一直转下去

**所以停机必须是客户端本地的事**，而且要有**多条互相独立的路径**：

| 路径 | 谁检测 | 触发条件 |
|---|---|---|
| A. 自己的连接断了 | **被控端本地**（WebSocket 的 close/error 事件） | 与服务器断开 |
| B. 服务器通知主控离开 | 服务器发现 → 推 `peer left` → **被控端本地**执行 | 主控关闭页面 / 主动退出 |
| C. 心跳超时 | **被控端本地**（8 秒没收到主控任何业务消息） | 网络黑洞、主控页面卡死、服务器假死 |

三条路径最终都走**同一个本地函数**（`session.js` 的 `_failSafe`），保证不会有一条漏掉。

**为什么路径 C 是必需的**：如果主控的机器直接断电，或者网络单向不通（能发不能收），
服务器可能以为连接还活着，被控端却已经收不到任何控制指令了。这时只有本地心跳超时能救。

**恢复策略**：停机后**不会自动恢复输出**，必须主控重新下发"启用"。
宁可让用户多操作一次，也不要让设备在无人确切掌控的情况下继续运行。

## 6. 可靠性设计

### 6.1 状态同步：变化驱动 + 回执确认 + 心跳保活

```
主控                                    被控
 │ 状态变化 → 发 STATE(rev, digest) ──────►│
 │                                        │ 应用 → 回 ACK(seq, digest)
 │ ◄──────────────────────────────────────│
 │ digest 一致 → 停止重传                   │
 │ digest 不一致 / 超时 → 退避重传           │
 │   300ms → 600ms → 1.2s → 2s（封顶）      │
 │                                        │
 │ 无变化时每 2 秒发 KEEPALIVE ────────────►│
 │ ◄──────────────────────────────────────│ 回 ACK（捎带状态）
```

**为什么"持续发送"和"回执确认"必须一起用**：

| 只用持续发送 | 只用变化+回执 | 合起来 |
|---|---|---|
| 漏包能兜住 | 省流量，但不知道对方死活 | 变化时发+重传（省流量） |
| 但永远不知道对方执行到哪一版 | 心跳断了会一直重传堆积 | + 无变化时心跳（保活） |

**被控端在 ACK 里带自己的 `seq`** → 主控因此知道"对方现在生效的是第几版"。
落后就立刻重传；异常超前则以被控为准并告警。

### 6.2 防止状态倒退

`rev` **单调递增**。被控端收到 `rev < 当前已生效 rev` 的消息时**直接忽略**，
并回一条 ACK 告诉主控自己当前的版本。

这防止了：网络乱序、服务器重放、中间人篡改导致的"状态倒退"。

### 6.3 波形只传一次

两端波形库是**各自独立的本地数据，ID 必然对不上**。所以用**内容指纹**（FNV-1a 哈希）做身份：

- 主控切换波形 → 先算指纹
- 被控已有该指纹 → 只发指纹 + 参数（几十字节）
- 被控没有 → 发完整波形定义（几百字节 ~ 几 KB）
- 主控收到 ACK 确认后，把该指纹记为"对端已拥有"，**之后不再重传**

**大波形分片**：超过 8KB 的载荷切成多片，每片一个独立 `relay`。
被控端集齐后**再走一次完整校验**（含指纹比对），**绝不允许应用半截波形** ——
半截波形可能导致强度异常。

### 6.4 流量预算（实测估算）

| 项 | 频率 | 单包 | 带宽 |
|---|---|---|---|
| 状态更新（含波形，仅变化时） | 每次操作 ~1 次 | 0.1~3 KB | 可忽略 |
| 重传（弱网） | 退避，最多 ~5 次 | 同上 | 低 |
| 心跳 + ACK | 0.5 Hz | ~90 字节 | ~45 B/s |
| 延迟/时钟测量 | 0.5 Hz | ~70 字节 | ~35 B/s |
| **合计** | | | **< 120 B/s** |

一分钟不到 7 KB，一小时约 400 KB。对任何服务器都是可忽略的量级。

## 7. 服务器内部结构

```
server.js
├── 配置加载        DEFAULTS 深合并 config.json + 环境变量
├── 日志器          createLogger()：分级 + 按大小/日期轮转 + 保留期清理
├── WebSocket 实现  RFC6455 握手 + 帧解析/编码（零依赖，自己写的）
│   ├── 支持文本帧 / 分片续帧 / close / ping / pong
│   ├── 客户端→服务端必须带掩码，正确解掩码
│   ├── 服务端→客户端不加掩码
│   └── 126/127 扩展长度
├── 连接表          conns: Map<peerId, conn>
├── 房间表          rooms: Map<roomCode, room>
│   └── room = { code, members: [], createdAt, lastAt }
├── 限流簿          rateBook: Map<'ip|rule', {start, count, warned}>
├── 计数器          counters: { msgsIn, msgsOut, ..., peakConns, peakRooms }
├── 消息分发        create / join / leave / relay / ping
├── 巡检定时器      扫死连接 + 扫空闲房间
└── HTTP 端点       /ws（升级） + /health（JSON） + 其它路径给说明文本
```

**房间用数组而不是"两个字段"**：`members: []` 是为将来放开多人预留的。
现在的转发逻辑是"房间内除自己外的所有成员"，放开多人时只改 `room.maxMembers` 即可。

**`trustProxy`**：部署在 Caddy/Nginx 后面时**必须为 `true`**，
否则 `req.socket.remoteAddress` 拿到的是反向代理的 IP（127.0.0.1），日志就没有追溯价值了。
开启后会从 `X-Forwarded-For` / `X-Real-IP` 里取真实客户端 IP。

## 8. 日志设计

**原则：够追溯，但不记录业务内容。**

### 记录什么

| 事件 | 关键字段 |
|---|---|
| 服务启动/停止 | 端口、版本、配置摘要 |
| `ws-open` | IP、peerId、浏览器名+大版本 |
| `room-create` / `room-join` | 房间号、IP、peerId、角色 |
| `msg.error` | 房间号、IP、peerId、错误码 |
| `ws-close` | 房间号、IP、peerId、**断开原因**、在线时长 |
| `room-reclaim` | 房间号、存活时长、成员数 |
| 限流触发 | IP、规则名 |
| 周期统计（5 分钟） | 在线房间数、连接数、消息计数、收发字节数 |
| 异常 | 错误类型、堆栈（截断）、关联 peerId/IP |

### 明确**不记录**

- ❌ `relay` 的 `payload` 内容（波形、强度、相位一律不落盘）
- ❌ 完整 User-Agent（只留 `Chrome/153` 这样的浏览器名+大版本）
- ❌ 任何用户自定义数据

### 实现细节

- **格式**：单行 JSON（`{ts, level, event, ...}`），便于 `grep` / `jq` / 日志系统采集
- **分级**：`error` / `warn` / `info`（默认）/ `debug`（需手动开）
- **轮转**：单文件超过 `maxFileBytes`（默认 10MB）或跨天时轮转，保留 `retainDays`（默认 14 天），自动清理
- **IP 模式**：`log.ipMode` 为 `full`（默认，记完整 IP 便于追溯滥用）或 `masked`（最后一段变 `x`）
- **分文件**：访问日志与错误日志分开，不混在标准输出里

### 为什么 `debug` 默认关闭

`debug` 级别会**逐条记录 relay**（只记字节数与目标数，不记内容）。那会让日志量暴涨
（20Hz 心跳下几分钟就能到几十 MB）。只在排查问题时临时打开。

## 9. 容量估算

按第 6.4 节的流量预算（每连接 < 120 B/s）和一个房间 2 个连接算：

| 资源 | 消耗 | 说明 |
|---|---|---|
| 内存 / 房间 | 约 1~2 KB | 两个 conn 对象 + 房间元数据 + 缓冲区 |
| 内存 / 连接 | 约 20~40 KB | Node 的 socket 缓冲 + 帧解析状态 |
| 带宽 / 房间 | 约 240 B/s | 双向合计 |

**一台 1 核 1GB 的轻量服务器：**

| 指标 | 估算 |
|---|---|
| 同时在线房间 | 数千个（受内存与 `server.maxConnections` 限制，默认 5000 连接 ≈ 2500 房间） |
| 出口带宽 | 2500 房间 ≈ 600 KB/s ≈ 5 Mbps |
| CPU | 极低 —— 只做转发，不做解析 |

**实际瓶颈通常是带宽而不是 CPU。** 阿里云轻量服务器一般有带宽上限（如 3~5 Mbps），
按上面的估算，**约 1500~2500 个同时在线房间**会打满带宽。
个人使用场景下这个上限远远够用。

> 如果将来真的不够：先调 `server.maxConnections` 限制，再考虑多实例 + 按房间号哈希分流。
> 但那是很远的事，现在不用做。

## 10. 安全边界（明确说清"不防什么"）

**服务器做到的：**
- 只在本机端口监听，`8787` 不对外暴露（由反向代理终止 TLS）
- 强制走 `wss://`，链路加密
- 每 IP 限流建房/加入，防滥建
- 畸形消息与超大消息直接断开，防内存耗尽
- 单连接累计畸形消息过多则断开

**服务器不做的（依赖客户端）：**
- **不做鉴权**：拿到房间号就能加入。房间号本身就是凭证 —— 请私聊发送
- **不校验业务内容**：强度是否合理等由客户端校验
- **不做端到端加密**：服务器能看到业务消息的明文（虽然不记录）。
  如果你连服务器都不信任，需要的是客户端加一层端到端加密，当前版本没做
- **不防中间人**：TLS 保护了链路，但服务器本身是可信第三方

**这些取舍是有意的**：这是一个 DIY 玩具项目的配套工具，服务器由使用者自己搭建或选择信任的人搭建。
把边界说清楚，比假装"很安全"更有用。
