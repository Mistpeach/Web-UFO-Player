# UFO 助手 · 打包与离线部署方案

> 目标：Windows 与 Android 上**双击就能跑、无需联网、无需配置**。
> 本文档只给方案与验证步骤，尚未落地任何打包产物。

---

## 0. 先搞清楚真正的约束（这决定了一切）

打包方式其实**不重要**，重要的是宿主环境能不能提供 `navigator.bluetooth`。

| 环境 | `navigator.bluetooth` | 结论 |
|---|---|---|
| 桌面 Chrome 56+ / Edge 79+ | ✅ 有 | 开箱可用（Windows 10 1703+） |
| **Chrome for Android 56+** | ✅ 有 | **移动端可以，要求 Android 6.0+** |
| Opera 43+ / Samsung Internet 6.2+ / Opera Mobile 64+ | ✅ 有 | 同样是可用宿主 |
| Firefox（桌面与移动） | ❌ 无 | 任何版本都不支持 |
| Safari（iOS / macOS） | ❌ 无 | 任何版本都不支持 |
| `file://` 双击本地 HTML | ⚠️ **待实测** | 见下方说明 |
| Electron（任意平台） | ❌ 无 | Electron 5+ 已移除 Web Bluetooth，issue 至今未关闭 |
| Tauri（WebView2 / WKWebView） | ❌ 无 | WebView2 没有 Web Bluetooth，[Tauri 官方讨论](https://github.com/tauri-apps/tauri/discussions/10529) 确认需自行接插件 |
| Android WebView | ❌ 无 | [WebView 不实现 Web Bluetooth](https://stackoverflow.com/questions/51678429/is-it-possible-to-use-web-bluetooth-from-a-webview) |

### Web Bluetooth 的门槛
1. **必须安全上下文** —— 规范把 `file://` 也列为 potentially trustworthy，因此 `window.isSecureContext` 在本地文件里**应为 true**
2. **必须由用户手势触发** —— 必须在按钮 click 里调 `requestDevice()`（本项目已经满足）
3. **必须有可用实现** —— 上面表格里 ❌ 的宿主一律没戏，跟 URL 方案无关

### ⚠️ 关于 `file://` —— 以实测为准
网络上能查到"静态本地 HTML 用不了 Web Bluetooth"的说法（[SO 提问](https://stackoverflow.com/questions/68670894/how-can-i-use-web-bluetooth-in-a-static-local-html-file)），但**本项目作者在 Windows Edge 上直接用 `file://` 打开就能连上设备**。

这两者不矛盾的可能性：该 SO 提问说的是**具体报错场景**（例如跨域、或早期 Chrome 版本的实现差异），而不是"一律禁止"。

**结论：不要采信任何二手结论，用 `docs/bt-check.html` 实测。** 如果 `file://` 可用，Windows 方案可以直接简化为"双击 index.html"，连本地服务器都不需要。

实测页面 `docs/bt-check.html` 会打印：`location.protocol`、`window.isSecureContext`、`navigator.bluetooth` 是否存在、`getAvailability()` 结果，并提供一个按钮真正发起一次 `requestDevice()` 来确认。

**所以：**
- Windows = 优先实测 `file://`；若不可用则退到 `http://127.0.0.1` → 两种情况下业务代码都**一行都不用改**
- Android = 见第 2 节，有两条路，**首选不需要写原生蓝牙的那条**

## 1. Windows 方案

### 方案 1-A：便携目录 + 启动器（推荐，改动最小）

目录结构：

```
UFO-Assistant/
├── 启动.bat            ← 双击这个
├── server.ps1          ← 或 server 小可执行文件
├── index.html
├── style.css
├── WaveControler/      ← 当前 live 文件直接复制
├── ScriptPlayer/
└── res/
```

启动器要做三件事：

1. 挑一个空闲端口（不要写死 8000，避免冲突）
2. 起一个只读静态服务器，根目录 = 本目录
3. 默认浏览器打开 `http://127.0.0.1:<端口>/index.html`

`启动.bat` 逻辑（优先用系统自带 PowerShell，无需装任何东西）：

```bat
@echo off
cd /d "%~dp0"
powershell -NoProfile -ExecutionPolicy Bypass -File "server.ps1"
```

`server.ps1` 要点：用 `System.Net.HttpListener` 实现静态文件服务（**纯系统组件，零安装**），监听 `127.0.0.1`（不要监听 `0.0.0.0`，避免局域网暴露），然后 `Start-Process` 打开默认浏览器，最后阻塞等待 Ctrl+C。

> 也可以用系统 Python（`python -m http.server`），但 PowerShell 方案不依赖任何外部运行时，更符合"免装"。

**优点**：零依赖、零构建、业务代码零改动、体积 ≈ 项目本身（650 KB）+ 启动脚本。
**缺点**：需要机器上有 Chrome/Edge（Windows 10/11 默认就有 Edge）。

### 方案 1-B：单文件 exe

把上面的启动器 + 静态服务器编译成一个 `.exe`（C# / Go 皆可，dotnet 与 Java 本机已具备）。用户机器上不需要 Python/PowerShell 之外的任何东西，但**仍然需要 Chrome/Edge** 来提供 Web Bluetooth。

如果想连浏览器一起打进去，就得内置 Chromium（CEF / WebView2 固定版本运行时），体积会涨到几百 MB，而且 CEF 是否需要编译期开关才能启用 Web Bluetooth **尚未验证**，不建议先走这条路。

### 方案 1-C：需要自己验证的 Electron 路线

Electron 虽然在 Windows 上**理论上**能通过 Chromium 的蓝牙栈工作，但：
- `navigator.bluetooth` 默认不可用
- 需要主进程监听 `select-bluetooth-device` 事件，**手动把 `candidate.deviceList` 回填给渲染进程**，Chromium 自己弹不出系统选择框
- 文件名过滤为 `UFO-TW` 时列表里通常只有一个设备，**可以先自动选中**，从而做到"无感连接"

主进程形如：

```js
mainWindow.webContents.on('select-bluetooth-device', (event, deviceList, callback) => {
  event.preventDefault();
  const hit = deviceList.find(d => d.deviceName === 'UFO-TW');
  if (hit) callback(hit.deviceId);           // 自动选中，用户无感
  else mainWindow.webContents.send('ble-devices', deviceList); // 交给页面兜底选择
});
```

**建议**：先把 1-A 落地跑通。等 1-A 稳定了，再决定值不值得为了"免装浏览器"去做 Electron 自适应层（代码量不大，但属于额外的坑）。

## 2. Android 方案

**前提更正：Chrome for Android 是支持 Web Bluetooth 的（56+，要求 Android 6.0+）。** 所以 Android 上不必写原生蓝牙代码 —— 只要想办法让页面在 Chrome 里以"有来源"的方式打开即可。

只有 **Android WebView 不行**（WebView 不实现 Web Bluetooth），所以"套个 WebView 的壳"是错的方向。

### 2-A：APK 内起本地服务器 + 交给系统 Chrome 打开（首选，零原生蓝牙）

思路：APK 里打包静态文件，启动时在本机起一个只读 HTTP 服务器（`http://127.0.0.1:<端口>`），然后用 `Intent` 拉起系统 Chrome 打开这个地址。

```
app/src/main/
├── AndroidManifest.xml
├── java/.../MainActivity.kt    ← 起本地服务器 + Intent 打开 Chrome
├── java/.../LocalServer.kt     ← 极简静态文件服务（NanoHTTPD 或自己写 ~100 行）
└── assets/www/                 ← 本项目静态文件原样放入（index.html / WaveControler / ScriptPlayer / res）
```

要点：
- 用 `ACTION_VIEW` + `setPackage("com.android.chrome")` 拉起 Chrome；没装 Chrome 就退到 `ACTION_VIEW` 让用户选浏览器
- 服务器只监听 `127.0.0.1`，并用随机端口；进程被杀时端口自然释放
- **零原生蓝牙代码**：`navigator.bluetooth` 由 Chrome 自己提供，`ble.js` 一行都不用改
- 代价：界面跑在 Chrome 里（会占用一个标签页），不是"独立 App 外观"

**这条路是本项目最省事、最不容易出错的 Android 方案。**

### 2-B：WebView + 自写原生 BLE 桥接（想要真正独立 App 时才做）

如果你的诉求是"看起来就是个 App、不跳 Chrome 标签页"，那 WebView 这条路必须自己把蓝牙补齐。

```
app/src/main/
├── AndroidManifest.xml
├── java/.../MainActivity.kt      ← WebView + 注入 shim
├── java/.../BleBridge.kt         ← 蓝牙扫描/连接/写特征值
└── assets/                       ← 本项目静态文件原样放入
```

**权限（Android 12+）**：

```xml
<uses-permission android:name="android.permission.BLUETOOTH_SCAN"
    android:usesPermissionFlags="neverForLocation" />
<uses-permission android:name="android.permission.BLUETOOTH_CONNECT" />
<!-- Android 11 及以下 -->
<uses-permission android:name="android.permission.BLUETOOTH" android:maxSdkVersion="30" />
<uses-permission android:name="android.permission.BLUETOOTH_ADMIN" android:maxSdkVersion="30" />
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" android:maxSdkVersion="30" />
```

**桥接层要暴露的接口** —— 正好对应本项目 `js/ble.js` 用到的三个调用：

| 页面调用 | 桥接要实现 |
|---|---|
| `navigator.bluetooth.requestDevice({filters:[{name:'UFO-TW'}]})` | `BluetoothLeScanner` 按名字过滤扫描 |
| `device.gatt.connect()` → `getPrimaryService(uuid)` → `getCharacteristic(uuid)` | 连 GATT、按 UUID 找服务与特征 |
| `characteristic.writeValueWithoutResponse(bytes)` | `WRITE_TYPE_NO_RESPONSE` 写特征值 |

**关键：可以不改业务代码。** 在 WebView 里注入一个 `navigator.bluetooth` 的 shim，形状与真实 API 一致，内部走 `addJavascriptInterface` 调 Kotlin。这样 `ble.js` 的 `connect()` / `send()` 原样复用，两个控制器（ScriptPlayer 与 WaveControler）都能用。

需要注意的差异：
- **`showDirectoryPicker()` 在 Android 不存在**（WebView 与 Chrome for Android 都没有）—— 波形控制器的"打开文件夹"批量导入要降级为 `<input type="file" multiple>`；`io.js` 里的 `pickFolderToImport` / `writeToFolder` 已有"不支持则提示"的分支，改成回退到多选文件即可。**注意 `writeToFolder`（批量写出到文件夹）在 Android 上没有等价能力，只能改成"逐个下载"**
- **切后台即断** —— Android 会冻结页面，引擎的 `visibilitychange` 安全停止逻辑会触发，与桌面行为一致，无需额外处理
- **WebView 需要 `WebChromeClient` / `WebSettings` 放开**：`domStorageEnabled`（localStorage 必须）、`javaScriptEnabled`、`allowFileAccess`（加载 assets 里的相对路径）
- **`AndroidManifest` 需处理 `target="_blank"`** —— `index.html` 用新标签打开控制器，WebView 里要 `shouldOverrideUrlLoading` 拦截，否则跳出应用
- **File System Access API**：`showDirectoryPicker` 不存在；`<input type="file">` 在 WebView 里需要 `onShowFileChooser` 才能弹出选择器

### 2-C：Capacitor 路线（不推荐）

Capacitor 有成熟的 BLE 插件（[capacitor-community/bluetooth-le](https://github.com/capacitor-community/bluetooth-le)），但它同样**不会给 WebView 带来 `navigator.bluetooth`** —— 你依然要写一层 shim 把调用转发到插件。既然横竖都要写桥接，直接用纯 Android 工程反而少一层依赖，也不需要引入 npm 工具链。

**另外：既然 Chrome for Android 本身就支持 Web Bluetooth，用 Capacitor 去换一个"不能用蓝牙的 WebView"是纯粹的倒退。2-A 才是正解。**

## 3. 落地顺序建议

| 阶段 | 内容 | 工作量 | 备注 |
|---|---|---|---|
| 0 | 用 `docs/bt-check.html` 实测 Windows Edge 的 `file://` 行为 | 极小 | **先做这个** —— 决定 Windows 要不要本地服务器 |
| 1 | 若 `file://` 可用 → Windows 直接就是"双击 index.html"，无需任何打包 | 无 | 最理想结果 |
| 1' | 若 `file://` 不可用 → 做方案 1-A（启动器 + 本地服务器） | 小 | 业务代码零改动 |
| 2 | Windows 真机跑通全流程（连蓝牙、开文件夹、播放） | 小 | |
| 3 | Android 方案 2-A（APK 内本地服务器 + Intent 拉起 Chrome） | 小到中 | **零原生蓝牙代码**，Android 首选 |
| 4 | Android 文件选择降级（多选文件替代文件夹） | 小 | 只影响波形控制器的批量导入/导出 |
| 5 | （仅当必须"独立 App 外观"）Android 方案 2-B：WebView + BLE 桥接 | 中大 | 核心工作量在这一步 |
| 6 | （可选）Electron 自适应层，去掉"必须装浏览器" | 中 | 需验证 `select-bluetooth-device` 行为 |

## 4. 未验证事项（动手前必须实测）

以下几条是本文档中**未经实机验证**的假设，落地时先各自做个最小验证：

- [ ] **Windows Edge / Chrome 的 `file://` 能否用 Web Bluetooth**（用 `docs/bt-check.html`）—— 决定 Windows 方案是"零打包"还是"需要本地服务器"
- [ ] 若走 1-A：`http://127.0.0.1:<端口>` 下能正常弹设备框，且 `showDirectoryPicker()` 可用
- [ ] **Chrome for Android 的 Web Bluetooth 在实际机型上能搜到 `UFO-TW` 并连接**（caniuse 显示支持，但需确认是否需要先在系统设置里配对）
- [ ] Android 方案 2-A：`Intent` 拉起 Chrome 打开 `http://127.0.0.1` 地址后，蓝牙权限与设备选择框行为是否正常
- [ ] Android 方案 2-B：Android 12+ 的 `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT` 运行时授权在 WebView 场景下的正确姿势
- [ ] Android 方案 2-B：WebView 长时间后台后 GATT 连接是否仍存活（可能需要前台服务保活）
- [ ] Electron 的 `select-bluetooth-device` 在当前 Electron 版本上仍可用且能自动选中
