# 远程控制功能 · 实施计划

> 状态：**仅计划**，尚未实施任何代码。
> 目标版本：v2.1（待定）

---

## 0. 先说清楚那个根本性技术障碍

**Web Bluetooth 无法被远程调用。**

`navigator.bluetooth` 只存在于**持有设备的那台机器上的那个浏览器**里。没有任何办法让另一台设备（手机、异地电脑）通过网页去操作用户本机浏览器的蓝牙连接。这不是实现难度问题，是浏览器安全模型决定的。

所以远程控制的**唯一可行形态**是：

```
                    BLE（本地、必须由本机浏览器持有）
[玩具 UFO-TW] ◄──────────────────────► [房主浏览器 = WaveApp]
                                              ▲
                                              │ 服务器中转（只转发状态，不碰蓝牙）
                                              ▼
                                        [远程浏览器 = RemoteApp]
```

**关键推论：房主的浏览器页面必须一直开着。** 它是蓝牙的唯一持有者，也是唯一的指令生成者。这一点必须在功能设计初期就告诉用户，不能让人以为"关掉网页也能被远程控制"。

**另一个关键推论（这条决定了整个架构）**：

> 远程控制**不需要实时流式传指令**。

因为波形是**参数化的**（波形 ID + 强度 + 相位 + 启停），不是逐帧数据。远程方只需要把「我要用哪个波形、强度多少、相位多少、开还是关」同步给房主；**实际的 20Hz 蓝牙发包依然由房主本地完成**。

这样做的结果：
- 远程方向上传的数据量极小（每次操作几字节，不是每秒 20 包）
- **网络延迟只影响"参数生效那一刻"的体感，完全不影响波形本身的质量**
- 弱网下不会出现抖动、丢包导致的动作卡顿

**这是整个方案的基石。** 如果按"远程逐帧转发 BLE 指令"来做，延迟和丢包会毁掉体验，而且没必要。

## 2. 架构设计

### 2.1 组件

| 组件 | 位置 | 职责 |
|---|---|---|
| **Host** | 现有 `WaveControler/WaveApp.html` | 唯一持有 BLE；本地 20Hz 生成指令；拥有最终否决权 |
| **Remote** | 新增 `WaveControler/RemoteApp.html` | 远程界面：选波形、调强度/相位、开关、急停、看遥测 |
| **Relay** | 新增 `server/worker.js`（Cloudflare） | 房间中转。**只转发 JSON 消息，不理解内容，不存储** |
| **Link** | 新增 `js/link.js` | 传输抽象：`BroadcastChannel`（本地调试）/ `WebSocket`（生产）两种实现，接口一致 |
| **Session** | 新增 `js/session.js` | 房间状态机：配对、权限、上限、心跳、看门狗、断线处理 |
| **Protocol** | 新增 `js/protocol.js` | 消息定义与校验（防畸形消息打崩页面） |

### 2.2 为什么要把传输抽象出来

**Phase 1 会先在同源的两个标签页之间用 `BroadcastChannel` 跑通全部逻辑 —— 不需要服务器。**

等协议、权限、看门狗都在本地验证通过了，Phase 3 只把 `BroadcastChannel` 换成 `WebSocket`，**业务逻辑一行不改**。这样能把"协议设计错误"和"网络问题"两类 bug 彻底分开调试。

### 2.3 消息协议（草案）

```js
// 房主 → 远程：完整状态快照（连接、波形、参数、遥测）
{ t:'state', rev:12,
  run:{ running:true, latched:false, mock:false },
  ch:{ A:{ enabled:true, intensity:0.8, phase:0, wave:{id,name,duration,mode,peak} },
       B:{ enabled:false, intensity:1.0, phase:0, wave:null } },
  limits:{ remoteMaxIntensity:0.5, remoteLocked:false },
  host:{ name:'房主的设备名（可选）' } }

// 房主 → 远程：低频遥测（1~2Hz，只用于远程画示波器，不参与控制）
{ t:'tick', a:83, b:-40 }

// 远程 → 房主：打补丁（只发变化的部分）
{ t:'set', rev:12, ch:'A', patch:{ intensity:0.6 } }      // 调参数
{ t:'enable', rev:12, ch:'A', on:true }                    // 开关输出
{ t:'wave', rev:12, ch:'A', id:'w_xxx' }                   // 换波形（房主校验存在性与只读性）
{ t:'stop' }                                               // 急停（单键，无需双击）

// 房主 → 远程：拒绝与说明
{ t:'denied', rev:12, reason:'intensity-over-limit' | 'lock' | 'no-wave' | 'rev-outdated' }

// 双向：心跳
{ t:'ping', at:12345 } / { t:'pong', at:12345 }
```

**设计要点：**
- 带 `rev`（状态版本号）：远程的补丁若基于过期状态，房主拒绝并回推最新快照，避免"两个人在改同一参数"打架
- 补丁式（只发变化字段），不是全量同步
- 所有远程指令**必须由房主校验后再执行**，服务器不参与任何判断

## 3. 安全设计（这部分不可协商）

| 机制 | 说明 |
|---|---|
| **房主最终否决权** | 房主按急停 → 立即归零 + **锁定远程**，直到房主手动解锁。远程无法解除 |
| **远程强度上限** | 房主可设远程能拉到的最大强度（**默认 50%**）。远程界面看不到上限值，也改不了；超限直接被拒并提示 |
| **权限清单** | 远程**不能**：连接/断开蓝牙、踢除房主、解除锁定、改上限、导出/删除波形、进入编辑器 |
| **看门狗** | 房主本地计时：超过 N 秒没收到远程心跳 → 视为断线 → **自动取消输出并补发停机**。不依赖服务器通知（服务器可能挂） |
| **不暴露设备信息** | 房间码用 6 位随机串，与设备 ID、蓝牙地址无关；`state` 里默认不包含本地文件路径等隐私 |
| **服务器不可信原则** | Relay 只做转发。房主对每条进来的消息都做校验（类型、字段、范围、rev），畸形消息直接丢弃 |
| **一次性配对** | 短码在会话结束后失效；房主可随时"结束会话"使链接全部失效 |
| **显式同意** | 远程页面首屏必须有明确说明："你正在申请控制他人设备"，房主端弹出**审批确认**后才建立会话 |

> ⚠️ 远程控制他人佩戴的设备涉及**同意与隐私**。这个功能上线时必须在房主端有明确的"当前有远程控制者在线"常驻提示，且房主的急停永远是最高优先级。这部分不做到位，功能就不该发布。

## 4. 实施阶段（每阶段可独立验证）

### Phase 0 · 定协议（不写功能代码）
- 敲定第 2.3 节的消息格式与字段取值范围
- 写出字段校验规则（每个字段的类型、范围、必填）
- **产出**：`js/protocol.js`（只有常量、`encode()`、`validate()`）
- **验证**：用纯数据跑一遍校验用例（Python 仿真即可，不需要浏览器）

### Phase 1 · 本地双标签页跑通（不接服务器）
- 实现 `js/link.js` 的 `BroadcastChannel` 实现
- 实现 `js/session.js`：房间状态机、快照推送、补丁校验、rev 冲突、看门狗
- 在 `WaveApp.html` 加「📡 远程控制」按钮 → 打开房间、显示短码（本地用标签页编号代替）
- 再开一个标签页用 `RemoteApp.html`（Phase 2 的雏形）加入
- **验证**：远程改强度 → 房主本地真的变；远程急停 → 本地归零且锁定；关掉远程标签页 → 看门狗触发停机
- **这是最重要的一步**：全部逻辑在此定型，且零服务器风险

### Phase 2 · 远程界面
- 新增 `RemoteApp.html` + `js/remoteui.js`
- 界面元素：连接状态、房主审批结果、波形库（只读列表）、A/B 强度与相位滑杆、启停开关、**大号急停按钮**、示波器（用 1~2Hz 遥测数据绘制，不追实时）
- 权限受限项置灰并给出原因
- **验证**：远程界面能完整反映房主状态；越权操作被拒且有明确提示

### Phase 3 · 接入 Cloudflare 房间服务
- 新增 `server/worker.js`：`/ws/<code>` 端点，Durable Object 维护房间成员与转发
- `js/link.js` 增加 `WebSocket` 实现，接口与 Phase 1 完全一致
- 房主端「创建房间」拿到 6 位短码与链接
- **验证**：一台设备开蓝牙当房主，另一台设备（手机 4G）用链接加入，全流程可用
- **注意**：Cloudflare Workers 需要一个 `wrangler` 配置与部署流程，项目目前**没有**这个文件

### Phase 4 · 配对与安全收口
- 房主审批加入请求（弹窗：某设备申请控制，是否允许）
- 强度上限设置 UI、远程锁定 / 解锁、踢人、结束会话
- 心跳间隔与看门狗超时的可调参数
- **验证**：跑一遍第 3 节的全部安全机制

### Phase 5 · 打磨与可选扩展
- 断线重连、状态恢复、房间内多人观战（只读）、控制权交接
- 房主端常驻"远程在线"指示

```
    ├── worker.js           ← Cloudflare Worker + Durable Object
    └── wrangler.toml       ← 部署配置（项目目前没有）
```

### 对现有文件的改动（力求最小）

**核心发现：`js/ui.js` 已经导出了 `selectWave` / `toggleCh` / `onIntensity` / `onPhase` / `emergencyStop` / `testPulse` 等操作接口，`state` 也暴露在 `WC.ui.state`。**

所以远程指令进来时，`session.js` **直接调用这些现成接口**即可 —— **不需要改动任何现有业务逻辑文件**。

预计改动只有：

| 文件 | 改动 | 规模 |
|---|---|---|
| `WaveApp.html` | 工具栏加「📡 远程控制」按钮；加"远程在线"提示条与审批弹窗 | 小 |
| `js/ui.js` | 末尾挂载 `session.js`；把内部状态整理成一个 `snapshot()` 供会话取用 | 小（纯新增，不改现有逻辑） |
| `js/engine.js` | 可能需要在 `valueOf` / `send` 处加一个"远程强度上限钳制"钩子 | 小（若上限在 session 层校验，则**零改动**） |

**目标：v1.1/v2.0 期间的教训是"改动扩散会引入新 bug"。这次严格约束在新增文件里。**

## 6. 延迟与性能预算

| 场景 | 网络往返 | 影响 |
|---|---|---|
| 同城 / 同网 | 10~50ms | 几乎无感 |
| 跨省 4G | 50~150ms | 调滑杆时手感略有滞后，但动作质量不受影响 |
| 弱网 / 高抖动 | 300ms+ | 参数生效慢；**波形本身依然由房主本地 20Hz 稳定输出** |

遥测（远程画示波器）只发 1~2Hz，即使丢几包也只是曲线断续，不会影响控制。

## 7. 风险与限制

| 风险 | 应对 |
|---|---|
| **房主页面必须常开** | 功能说明里必须写清楚；房主关闭页面 = 会话结束 + 停机 |
| 服务器成为单点故障 | 看门狗不依赖服务器；服务器挂了 → 房主本地超时停机，不会失控 |
| 打破"零后端"现状 | README 与风险提示需明确说明；服务器代码开源、可自建 |
| 隐私（波形数据经服务器） | 只传必要字段（波形名、时长、模式、断点）；**不传本地文件路径**；服务器不落盘 |
| 弱网下授权被重放 | 每房间一次性短码 + rev 校验 + 房主端校验字段范围 |
| 多人竞争同一参数 | rev 冲突时拒绝并回推最新快照 |
| 越权/失控 | 房主的急停与锁定是最高优先级；远程永远无法解除 |
| **合规与同意** | 房主端必须有常驻的"远程在线"提示；远程端首屏必须明确说明用途 |
